# Batch 5 — Smart Contracts & Solidity
> Writing, deploying, and upgrading code that runs trustlessly on-chain.

---

## 1. Smart Contract

**A self-executing program stored on the blockchain that runs automatically when predefined conditions are met — no middleman needed.**

### Real-World Dev Example
An escrow contract holds ETH and releases it to the seller only when the buyer confirms delivery. No bank, no lawyer.

```solidity
// Simplified escrow
contract Escrow {
    address public buyer;
    address public seller;
    bool public delivered;

    function confirmDelivery() external {
        require(msg.sender == buyer);
        delivered = true;
        payable(seller).transfer(address(this).balance);
    }
}
```

### ASCII Diagram
```
User → calls function → EVM executes code → state changes on-chain
                             ↓
                    No one can stop it mid-execution
```

### Gotchas & Dev Context
- Once deployed, code is immutable (unless you use a proxy pattern)
- Execution costs gas — every opcode has a price
- Smart contracts cannot initiate actions themselves; they only react to calls
- Bugs are expensive: the DAO hack drained $60M

### Production FAQ
**Q: Can a smart contract call external APIs?**
A: Not directly. You need an oracle (e.g., Chainlink) to bring off-chain data on-chain.

**Q: Is a smart contract always trustless?**
A: Only if it has no privileged `owner` who can rug-pull. Audit the admin controls.

## 2. Solidity

**The primary high-level, statically-typed programming language for writing Ethereum smart contracts — think "JavaScript meets C++ for the blockchain."**

### Real-World Dev Example
Writing an ERC-20 token contract in Solidity:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract MyToken {
    string public name = "MyToken";
    mapping(address => uint256) public balanceOf;

    constructor(uint256 supply) {
        balanceOf[msg.sender] = supply;
    }
}
```

### Gotchas & Dev Context
- Always pin your `pragma` version — `^0.8.20` means "0.8.20 and up but not 0.9.x"
- Solidity 0.8+ has built-in overflow/underflow protection (no more SafeMath needed)
- Compiler versions change behavior — a contract compiled on 0.7.x may behave differently on 0.8.x
- Use [Hardhat](https://hardhat.org) or [Foundry](https://book.getfoundry.sh) for local development

### Production FAQ
**Q: Which Solidity version should I use in production?**
A: Use the latest stable release (e.g., `0.8.24`). Older versions miss security patches.

**Q: Is Solidity only for Ethereum?**
A: No — any EVM-compatible chain (Polygon, Arbitrum, BNB Chain) uses Solidity.

## 3. Vyper

**A Python-like smart contract language for Ethereum focused on security, simplicity, and auditability — deliberately less powerful than Solidity.**

### Real-World Dev Example
Curve Finance's core AMM contracts are written in Vyper because the team prioritized auditability over flexibility.

```python
# Vyper syntax (not Solidity)
# @version 0.3.10
owner: address

@external
def __init__():
    self.owner = msg.sender

@external
def greet() -> String[20]:
    return "Hello from Vyper"
```

### ASCII Diagram
```
Solidity: Full-featured, more footguns
Vyper:    Restricted, safer defaults, easier to audit
```

### Gotchas & Dev Context
- No class inheritance in Vyper — intentional, reduces attack surface
- No inline assembly — prevents low-level footguns
- Smaller ecosystem, fewer libraries vs. Solidity
- Re-entrancy guard is built-in by default
- Tooling (Ape Framework, Titanoboa) is maturing but smaller

### Production FAQ
**Q: Should I choose Vyper over Solidity?**
A: Only if security and auditability are your top priority and you're comfortable with fewer ecosystem tools.

**Q: Can Vyper and Solidity contracts interact?**
A: Yes — compiled bytecode is EVM-compatible; they can call each other via ABI.

## 4. ABI (Application Binary Interface)

**A JSON description that tells the outside world what functions and events a contract exposes — the "API schema" for your smart contract.**

### Real-World Dev Example
When you use `ethers.js` to call a contract, you pass the ABI so the library knows how to encode your function call:

```js
const contract = new ethers.Contract(address, ABI, signer);
await contract.transfer(recipient, amount);
```

### ASCII Diagram
```
Frontend / Script
      │
      │  (uses ABI to encode call)
      ▼
[ function selector + encoded args ] ──→ Contract on EVM
      ◀──────────────────────────────── [ decoded return value ]
```

### Gotchas & Dev Context
- The ABI is generated by the Solidity compiler — don't write it by hand
- If you upgrade a contract and the ABI changes, old frontends will break
- Only `public` and `external` functions appear in the ABI
- Events are also part of the ABI (used for log decoding)
- ABIs do not include internal logic — just signatures

### Production FAQ
**Q: Where do I get the ABI for a deployed contract?**
A: If verified on Etherscan, you can fetch it via their API. Otherwise, compile the source yourself.

**Q: What happens if I call a function with the wrong ABI?**
A: The call either reverts (wrong selector) or silently returns garbage data.

## 5. Contract Deployment

**The act of sending a special transaction to the network that creates a new smart contract at a unique address — storing its bytecode permanently on-chain.**

### Real-World Dev Example
Using Hardhat Ignition or a deploy script:

```js
// Hardhat deploy script
const MyContract = await ethers.getContractFactory("MyContract");
const contract = await MyContract.deploy(constructorArg);
await contract.waitForDeployment();
console.log("Deployed to:", await contract.getAddress());
```

### ASCII Diagram
```
Deploy Tx (bytecode + constructor args)
        │
        ▼
   EVM runs initcode
        │
        ▼
   Contract address assigned (deterministic from sender + nonce)
        │
        ▼
   Runtime bytecode stored at that address forever
```

### Gotchas & Dev Context
- Deployment costs gas — large contracts cost more
- The address is derived from `keccak256(sender, nonce)` unless using CREATE2
- Deploying to testnet first is not optional — always test on Sepolia/Holesky
- Store your deployment addresses — you can't re-derive them easily
- Failed constructor reverts = no contract is created, but gas is still spent

### Production FAQ
**Q: Can I re-deploy to the same address?**
A: Not with CREATE (nonce changes). Use CREATE2 with the same salt + bytecode hash.

**Q: Who "owns" a deployed contract?**
A: Nobody by default. Ownership is a pattern you implement explicitly (e.g., OpenZeppelin's `Ownable`).

## 6. Constructor

**A special function that runs exactly once — during deployment — used to set initial state like ownership, token supply, or configuration.**

### Real-World Dev Example

```solidity
contract Vault {
    address public owner;
    uint256 public fee;

    constructor(uint256 _fee) {
        owner = msg.sender; // whoever deploys becomes owner
        fee = _fee;
    }
}
```

### Gotchas & Dev Context
- The constructor is NOT stored in the deployed bytecode — it runs once and disappears
- It can accept ETH if marked `payable`
- If you forget to set `owner` in the constructor, the contract may be ownerless and bricked
- In proxy patterns, the constructor of the **implementation** contract doesn't run on the proxy — use `initialize()` instead
- Constructors cannot be called after deployment

### ASCII Diagram
```
Deploy Transaction
    │
    ▼
Constructor runs (sets state)
    │
    ▼
Constructor code discarded
    │
    ▼
Runtime bytecode stored — no constructor visible
```

### Production FAQ
**Q: Can a constructor fail?**
A: Yes. If a `require()` inside the constructor fails, the deployment reverts and no contract is created.

**Q: Why use `initialize()` instead of `constructor()` in proxies?**
A: The proxy delegates calls to the implementation — the impl's constructor never runs in proxy context. `initialize()` fills that role explicitly.

## 7. Fallback & Receive Functions

**Special functions that handle ETH sent to a contract without a matching function call — your contract's "catch-all" handlers.**

### Real-World Dev Example

```solidity
contract ETHCatcher {
    event Received(address sender, uint256 amount);
    event FallbackCalled(bytes data);

    // Called when ETH is sent with no calldata
    receive() external payable {
        emit Received(msg.sender, msg.value);
    }

    // Called when no function matches, or ETH sent with calldata
    fallback() external payable {
        emit FallbackCalled(msg.data);
    }
}
```

### ASCII Diagram
```
Incoming call to contract
        │
        ├─ msg.data is empty + ETH sent? ──→ receive()
        │
        └─ no matching function?         ──→ fallback()
```

### Gotchas & Dev Context
- Without `receive()`, sending plain ETH reverts — you MUST implement it if you want to accept ETH
- `fallback()` has a 2300 gas limit when triggered by `transfer()` or `send()` — not enough for complex logic
- Many hacks exploit unexpected fallback execution (e.g., re-entrancy via fallback)
- Only one `receive` and one `fallback` allowed per contract

### Production FAQ
**Q: What if I send ETH to a contract with no receive or fallback?**
A: The transaction reverts. ETH is returned (minus gas).

**Q: Can I use the fallback to proxy all calls?**
A: Yes — this is exactly how proxy contracts work (delegate all unknown calls to implementation).

## 8. Function Modifiers

**Reusable code blocks that wrap around functions — used to enforce conditions (like access control) before or after a function executes.**

### Real-World Dev Example

```solidity
contract Guarded {
    address public owner;

    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _; // function body runs here
    }

    modifier nonZeroAmount(uint256 amount) {
        require(amount > 0, "Zero not allowed");
        _;
    }

    function withdraw(uint256 amount) external onlyOwner nonZeroAmount(amount) {
        payable(owner).transfer(amount);
    }
}
```

### Gotchas & Dev Context
- `_;` marks where the original function body is injected — its placement matters
- Stacking multiple modifiers runs them top-to-bottom
- Overusing modifiers makes code harder to read and debug
- OpenZeppelin's `ReentrancyGuard` is implemented as a modifier
- Avoid heavy logic in modifiers — keep them lean

### Production FAQ
**Q: Can modifiers have return values?**
A: No. Modifiers can only alter control flow. Return values come from the function itself.

**Q: What's the difference between a modifier and an internal function for checks?**
A: Functionally similar; internal functions are easier to test in isolation. Use modifiers for cross-cutting concerns like auth.

## 9. Events & Logs

**Events are Solidity's way of emitting structured log entries to the blockchain — cheap storage used by frontends and indexers to track what happened.**

### Real-World Dev Example

```solidity
contract Token {
    event Transfer(address indexed from, address indexed to, uint256 value);

    function transfer(address to, uint256 value) external {
        // ... transfer logic ...
        emit Transfer(msg.sender, to, value);
    }
}
```

```js
// Listening in ethers.js
contract.on("Transfer", (from, to, value) => {
    console.log(`${from} → ${to}: ${value}`);
});
```

### Gotchas & Dev Context
- Events are NOT readable from within the contract — they're external records only
- `indexed` parameters can be filtered efficiently (up to 3 per event)
- Logs cost much less gas than storage (~375 gas vs ~20,000 gas per slot)
- The Graph Protocol indexes events for complex queries
- Removing or renaming events in an upgrade breaks existing indexers

### Production FAQ
**Q: Can smart contracts read their own past events?**
A: No. Use The Graph, Moralis, or your own node to query logs off-chain.

**Q: Are events permanent?**
A: Yes — logs are part of the transaction receipt and stored in the blockchain, but pruned nodes may not keep them indefinitely.

## 10. Storage vs Memory vs Calldata

**Solidity's three data locations — where a variable lives determines its cost, lifetime, and mutability.**

### Real-World Dev Example

```solidity
contract DataLocations {
    uint256[] public stored; // lives in storage (persistent, expensive)

    function process(uint256[] calldata input) external {
        // calldata: read-only, cheapest for external args
        uint256[] memory temp = new uint256[](input.length); // memory: temp, cheaper
        for (uint i = 0; i < input.length; i++) {
            temp[i] = input[i] * 2;
        }
        stored = temp; // write back to storage
    }
}
```

### ASCII Diagram
```
┌──────────────────────────────────────────────┐
│ STORAGE  — on-chain, persistent, ~20k gas/slot│
│ MEMORY   — in-function scratch pad, erased    │
│ CALLDATA — read-only input from caller, cheap │
└──────────────────────────────────────────────┘
```

### Gotchas & Dev Context
- Using `storage` when you meant `memory` for a local variable can cause unintended mutations
- Calldata is cheapest — always prefer it for external function array/string params
- Memory arrays have a fixed size once created
- Stack is a 4th implicit location — limited to 16 local variables before "stack too deep" error

### Production FAQ
**Q: When should I use `memory` vs `calldata` for function parameters?**
A: `calldata` for `external` functions (read-only, cheaper); `memory` for `public` or when you need to modify the input.

**Q: Why is storage so expensive?**
A: Writing to storage modifies global blockchain state — every node must record and replicate it.

## 11. Mappings

**A key-value hash table built into Solidity — like a dictionary that maps one type to another, with O(1) lookup and no iteration.**

### Real-World Dev Example

```solidity
contract Ledger {
    mapping(address => uint256) public balances;
    mapping(address => mapping(address => uint256)) public allowances; // nested

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function getAllowance(address owner, address spender) external view returns (uint256) {
        return allowances[owner][spender];
    }
}
```

### Gotchas & Dev Context
- Mappings have **no length** and cannot be iterated — every possible key exists and defaults to zero
- You cannot delete a mapping wholesale — only individual keys
- Mappings cannot be returned from public functions or passed as arguments (except storage pointers)
- To iterate, maintain a separate array of keys alongside the mapping
- Nested mappings (mapping of mappings) are common for allowances (ERC-20)

### Production FAQ
**Q: How do I check if a key exists in a mapping?**
A: You can't directly — all keys "exist" with a zero/default value. Use a secondary `bool` mapping or a sentinel value.

**Q: Are mappings gas-efficient?**
A: Yes for individual lookups. The slot is computed as `keccak256(key, slot)` — zero-cost for non-existent keys.

## 12. Structs & Enums

**Structs group related variables into a single type; Enums define a fixed set of named states — both make your contract code cleaner and self-documenting.**

### Real-World Dev Example

```solidity
contract OrderBook {
    enum Status { Pending, Filled, Cancelled }

    struct Order {
        address trader;
        uint256 amount;
        uint256 price;
        Status status;
    }

    mapping(uint256 => Order) public orders;
    uint256 public orderCount;

    function placeOrder(uint256 amount, uint256 price) external {
        orders[orderCount++] = Order(msg.sender, amount, price, Status.Pending);
    }
}
```

### Gotchas & Dev Context
- Structs stored in storage are laid out slot-by-slot — pack small types together to save gas
- Enums compile down to `uint8` — max 256 values
- Default enum value is the first member (index 0) — design your state machine accordingly
- Passing structs between `internal` functions is fine; `external` functions require ABI encoding
- Structs with dynamic fields (arrays, mappings) are trickier to copy

### Production FAQ
**Q: Can I add new fields to a struct after deployment?**
A: Not safely in a regular contract. In a proxy pattern, you can append fields but never insert or reorder.

**Q: Can enums be used in events?**
A: Yes, but they're emitted and decoded as their underlying `uint8`.

## 13. Inheritance & Interfaces

**Inheritance lets contracts reuse and extend other contracts; interfaces define a contract's external shape without any implementation — Solidity's version of abstract APIs.**

### Real-World Dev Example

```solidity
// Interface — just the shape
interface IERC20 {
    function transfer(address to, uint256 value) external returns (bool);
    function balanceOf(address account) external view returns (uint256);
}

// Base contract
abstract contract Ownable {
    address public owner;
    constructor() { owner = msg.sender; }
    modifier onlyOwner() { require(msg.sender == owner); _; }
}

// Concrete contract inheriting both
contract MyToken is Ownable, IERC20 {
    mapping(address => uint256) private _balances;

    function transfer(address to, uint256 value) external override returns (bool) {
        _balances[msg.sender] -= value;
        _balances[to] += value;
        return true;
    }

    function balanceOf(address account) external view override returns (uint256) {
        return _balances[account];
    }
}
```

### Gotchas & Dev Context
- Solidity supports multiple inheritance — use C3 linearization order (most-derived first)
- All interface functions must be implemented, or the contract must be `abstract`
- Interfaces are the standard way to safely interact with external unknown contracts
- `virtual` marks a function as overridable; `override` marks it as overriding a parent

### Production FAQ
**Q: Interface vs abstract contract — when to use which?**
A: Interfaces for external interaction shape (no state, no implementation). Abstract contracts when you want shared logic + required overrides.

## 14. Library Contracts

**Reusable, stateless code collections deployed once and called by many contracts — like npm packages baked into the blockchain.**

### Real-World Dev Example

```solidity
library MathLib {
    function percentOf(uint256 amount, uint256 bps) internal pure returns (uint256) {
        return (amount * bps) / 10_000;
    }
}

contract Fee {
    using MathLib for uint256;

    function calcFee(uint256 amount) public pure returns (uint256) {
        return amount.percentOf(250); // 2.5% fee
    }
}
```

### ASCII Diagram
```
Contract A ──┐
Contract B ──┼──→  Library (deployed once at address X)
Contract C ──┘         stateless, shared logic
```

### Gotchas & Dev Context
- `internal` library functions are inlined at compile time — no external call needed
- `external`/`public` library functions require the library to be deployed separately and linked
- Libraries cannot hold state or receive ETH
- `using LibName for TypeName` adds library functions as methods on that type
- OpenZeppelin's `SafeERC20`, `Address`, `Strings` are classic library examples

### Production FAQ
**Q: Do I pay deployment costs for an internal library?**
A: No — internal functions are copied into the contract at compile time, not separately deployed.

**Q: What's "linking" in the context of libraries?**
A: The process of wiring a contract's external library calls to the deployed library address, done during deployment.

## 15. Proxy Pattern (Upgradeable Contracts)

**A pattern where users interact with a lightweight Proxy contract that delegates all calls to a swappable Implementation contract — enabling upgrades without changing the contract address.**

### Real-World Dev Example
A DeFi protocol deploys `VaultProxy` pointing to `VaultV1`. When a bug is found, they deploy `VaultV2` and update the proxy's implementation pointer — users never change their contract address.

### ASCII Diagram
```
User
 │
 ▼
Proxy Contract (stable address, holds state)
 │  delegatecall
 ▼
Implementation Contract (logic only, no state)
         │
         ▼ (upgrade)
Implementation V2
```

### Gotchas & Dev Context
- State lives in the **proxy**, logic lives in the **implementation**
- Storage layout must be identical between versions — adding fields is safe, reordering is catastrophic
- Never use constructors in implementations — use `initialize()` with an `initializer` modifier
- Use OpenZeppelin's Upgrades Plugin to detect storage collisions
- Proxy upgrades are centralized unless you use a DAO/timelock — a trust assumption many users miss

### Production FAQ
**Q: If my logic contract has a bug, does the proxy protect users?**
A: Only until you deploy a fix. The proxy itself must be bug-free — it's immutable.

**Q: Can a proxy be made non-upgradeable?**
A: Yes — renounce or lock the admin role to freeze it permanently.

## 16. UUPS vs Transparent Proxy

**Two competing proxy upgrade patterns that differ in where the upgrade logic lives — UUPS puts it in the implementation, Transparent puts it in the proxy itself.**

### ASCII Diagram
```
Transparent Proxy:
  Admin call   → handled by proxy (upgrade logic here)
  User call    → delegated to implementation

UUPS Proxy:
  Any call     → delegated to implementation
  Upgrade call → implementation checks auth, upgrades itself
```

### Gotchas & Dev Context

| Feature | Transparent Proxy | UUPS |
|---|---|---|
| Upgrade logic lives in | Proxy | Implementation |
| Gas cost per call | Higher (admin check) | Lower |
| Risk if impl is bricked | Proxy still upgradeable | Contract is permanently locked |
| OZ support | `TransparentUpgradeableProxy` | `UUPSUpgradeable` |

- Transparent proxies have a "function selector clash" mitigation — admin calls are intercepted
- UUPS is now the recommended standard (cheaper, cleaner)
- With UUPS, if you forget `_authorizeUpgrade()` in your implementation, nobody can upgrade

### Production FAQ
**Q: Which should I use in a new project?**
A: UUPS — lower gas, cleaner separation. Use OpenZeppelin's `UUPSUpgradeable` base contract.

**Q: Can I migrate from Transparent to UUPS?**
A: Yes, but it requires a careful upgrade step. OpenZeppelin docs cover the migration path.

## 17. Diamond Pattern (EIP-2535)

**An advanced proxy pattern that routes function calls to multiple implementation contracts ("facets") based on function selector — enabling truly modular, unlimited-size upgradeable contracts.**

### ASCII Diagram
```
                 ┌──────────────────────────────┐
User call ──→   │  Diamond Proxy               │
                │  (selector → facet mapping)  │
                └──────────┬───────────────────┘
                           │
         ┌─────────────────┼──────────────────┐
         ▼                 ▼                  ▼
    FacetA            FacetB             FacetC
  (token logic)   (governance)        (staking)
```

### Gotchas & Dev Context
- Each "facet" is a separate deployed contract handling a subset of function selectors
- `DiamondStorage` pattern avoids storage collisions using a unique storage slot per facet
- Adds considerable complexity — overkill for most projects
- Used by projects that exceed the 24KB contract size limit
- Louper.dev is a Diamond inspector tool for debugging facet layouts
- The "Diamond Cut" is the upgrade operation — adding/replacing/removing facets

### Production FAQ
**Q: When should I actually use the Diamond pattern?**
A: When your contract logic is too large for a single file (>24KB) or you need granular, independent upgrades per module.

**Q: Is the Diamond pattern audited and safe?**
A: The pattern itself is battle-tested, but each implementation needs careful auditing — the complexity increases risk.

## 18. Delegatecall

**A low-level EVM call that runs another contract's code in the current contract's context — the called contract reads and writes the caller's storage, not its own.**

### Real-World Dev Example

```solidity
contract Logic {
    uint256 public value; // slot 0

    function setValue(uint256 v) external {
        value = v; // writes to CALLER's slot 0
    }
}

contract Proxy {
    uint256 public value; // slot 0 — SAME slot as Logic.value

    address logic;

    constructor(address _logic) { logic = _logic; }

    fallback() external {
        (bool ok,) = logic.delegatecall(msg.data);
        require(ok);
    }
}
```

### Gotchas & Dev Context
- `msg.sender` and `msg.value` are preserved from the original caller — unlike a regular `call`
- Storage layout alignment is critical — slot 0 in logic maps to slot 0 in proxy
- The infamous Parity Multisig hack exploited delegatecall unexpectedly
- Never delegatecall to untrusted contracts — they can wipe your storage

### Production FAQ
**Q: What's the difference between `call` and `delegatecall`?**
A: `call` runs code in the called contract's own context. `delegatecall` runs the code in YOUR context (your storage, your balance).

**Q: Why does every proxy use delegatecall?**
A: It's the only way to execute foreign logic while keeping state in the proxy contract.

## 19. CREATE vs CREATE2 (Deterministic Deployment)

**CREATE generates a contract address from sender + nonce; CREATE2 generates it from sender + salt + bytecode hash — allowing you to know the address before deploying.**

### ASCII Diagram
```
CREATE:
  address = keccak256(sender, nonce)[12:]
  (nonce changes each tx — unpredictable)

CREATE2:
  address = keccak256(0xff, sender, salt, keccak256(bytecode))[12:]
  (deterministic — same inputs → same address, always)
```

### Real-World Dev Example

```solidity
// Using CREATE2 from a factory
contract Factory {
    function deploy(bytes32 salt, bytes memory bytecode) external returns (address addr) {
        assembly {
            addr := create2(0, add(bytecode, 0x20), mload(bytecode), salt)
        }
        require(addr != address(0), "Deploy failed");
    }
}
```

### Gotchas & Dev Context
- Uniswap V2 uses CREATE2 so pair addresses can be computed off-chain without contract calls
- Counterfactual deployment: you can send funds to an address before the contract exists
- Same bytecode + same salt from same deployer = same address, even on different chains (useful for cross-chain deployments)
- If bytecode changes (even a comment), the address changes

### Production FAQ
**Q: Can I redeploy to the same CREATE2 address?**
A: Only if the previous contract was self-destructed — then the same salt + bytecode redeploys to the same address.

**Q: Is CREATE2 more expensive than CREATE?**
A: Slightly — extra hashing. Usually negligible.

## 20. Contract Size Limit (24KB)

**The EVM enforces a hard limit of 24,576 bytes (~24KB) for deployed contract bytecode — hit this ceiling and your deployment reverts.**

### Real-World Dev Example
A complex DeFi protocol with dozens of functions, events, and complex math may exceed 24KB. Solutions:

```solidity
// Option 1: Split into multiple contracts
contract CoreLogic { /* main functions */ }
contract HelperLogic { /* utility functions */ }

// Option 2: Use libraries (internal functions are inlined, external are linked)
library ComplexMath { ... }
contract Main {
    using ComplexMath for uint256;
}
```

### Gotchas & Dev Context
- The limit applies to **deployed runtime bytecode**, not source code lines
- Long custom error strings and revert messages bloat bytecode — use custom errors instead:
  ```solidity
  error Unauthorized(); // cheaper than require(false, "Unauthorized")
  ```
- Enable the Solidity optimizer (`runs: 200`) to reduce bytecode size
- `forge build --sizes` or `hardhat-contract-sizer` plugin reports contract sizes
- Proxy/Diamond patterns are a structural solution for contracts that genuinely need more logic

### Production FAQ
**Q: How do I check my contract's size before deploying?**
A: Run `forge build --sizes` (Foundry) or install `hardhat-contract-sizer`. Keep a size budget per contract.

**Q: Will the 24KB limit ever be raised?**
A: EIP-3860 (initcode limit) was introduced but the deploy limit remains. There's no active EIP to raise it — use architectural patterns instead.
